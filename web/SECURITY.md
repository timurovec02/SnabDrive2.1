## 2. Что уже было сделано хорошо (не трогал)

- Все страницы и контроллеры требуют авторизацию: `[Authorize]` на каждом контроллере
  плюс глобальный `FallbackPolicy = RequireAuthenticatedUser`, поэтому новая страница
  «забытая» без атрибута всё равно не откроется анонимно.
- SignalR-хаб `[Authorize]` — список онлайн-пользователей не отдаётся без входа.
- Скачивание вложений — параметризованный запрос (`@id`), потоковая отдача без загрузки файла в память.
- Открытое перенаправление на входе закрыто (`ToSafeLocalUrl` принимает только локальные
  относительные адреса, `//` и `/\` отвергаются) — теперь это закреплено тестами.
- Страница `/error` не показывает ни стектрейса, ни текста исключения.
- Swagger подключается только в Development.
- Blazor экранирует вывод по умолчанию; `MarkupString` в проекте нет ни одного — это значит,
  что вставить исполняемый HTML из данных реестра в страницу нельзя.

## 3. Найденные проблемы

### 3.1 КРИТИЧНО: пароль базы данных в истории git

В первом же коммите (`4b3b4a6`, файл `SnabDriveDBContext.cs` старого WPF-проекта) была строка:

```
Data Source = 192.168.23.163,1433; Initial Catalog = SnabDriveDB; User ID = Admin; Password = 1234; ...
```

Файл удалён в коммите `893587d`, но объект остался в истории и доступен любому, у кого есть
доступ к репозиторию (`git show 4b3b4a6:SnabDriveDBContext.cs`).

Что сделано и что осталось:

- **Сделано:** в текущем коде зашитых строк подключения нет; проверка истории по всем 148 коммитам
  (700 уникальных файлов конфигурации и кода) других секретов не нашла — ни API-ключей,
  ни токенов, ни вебхуков Битрикс24, ни приватных ключей.
- **Осталось вам:** сменить пароль `Admin` (лучше — завести отдельную учётку `snabdrive_app`
  с правами только на `snabdrive_db`) и закрыть порт 1433 от всех, кроме сервера приложений.
  Пароль `1234` подбирается за секунды, адрес сервера в репозитории тоже указан.
- **Переписывать историю git не стал намеренно:** это force-push на 148 коммитов, который
  сломает вашу локальную копию и историю ветки, а пароль от этого не перестанет быть
  скомпрометированным. Если репозиторий публичный — скажите, подготовлю `git filter-repo`.

Внутренний адрес `192.168.23.163` встречается также в `web/README.md`, `web/docs/SSMS.md`
и `appsettings.SqlServer.example.json` — это не секрет, но лишняя информация о сети.

### 3.2 ВЫСОКИЙ: администратор с паролем из репозитория

В `appsettings.json` лежали `"SeedAdminPassword": "ChangeMe-123!"` вместе с
`"SeedRolesAndAdmin": true`. На новом сервере сайт создал бы администратора
`admin / ChangeMe-123!` — пароль известен всем, кто видел репозиторий.

**Исправлено:** значение в репозитории очищено. Логика посева теперь:

- пароль пустой → администратор не создаётся, в журнал пишется понятная инструкция
  (задать `Database__SeedAdminPassword`);
- пароль короче 10 символов или совпадает со списком известных (`ChangeMe-123!`, `admin`,
  `Admin123!`, `P@ssw0rd` и т.п.) → администратор не создаётся, в журнал пишется ошибка;
- администратор уже существует → пароль из конфигурации игнорируется.

**Важно:** если вы разворачиваете сайт на пустой базе, задайте переменную окружения
`Database__SeedAdminPassword` (или значение в `appsettings.Production.json`), запустите сайт
один раз, войдите, смените пароль и уберите переменную. На вашей действующей базе администратор
уже есть — посев просто не сработает, и ничего не сломается.

### 3.3 ВЫСОКИЙ: CSRF в Web API

Логин и выход antiforgery-токен проверяли, а семь контроллеров API — нет: любой сторонний сайт
мог отправить от имени вошедшего пользователя POST/PUT/DELETE с его cookie. Частично это
закрывал `SameSite=Lax`, но защита должна быть явной.

**Исправлено:** глобальный фильтр `AutoValidateAntiforgeryToken` — теперь все
POST/PUT/PATCH/DELETE в API требуют токен (в поле формы `__RequestVerificationToken`
или в заголовке `RequestVerificationToken`). GET/HEAD/OPTIONS не проверяются.
Для клиентов (Swagger, внешние скрипты) добавлен `GET /account/antiforgery-token` —
возвращает токен только авторизованному.

### 3.4 СРЕДНИЙ: любой тип загружаемого файла

Размер вложений проверялся на сервере (20 МБ), а тип — нет: можно было загрузить
`.exe`, `.html`, `.svg`, `.ps1`. Файл отдавался с `Content-Disposition: attachment`,
то есть браузер его скачивал, а не выполнял, но `.html`/`.svg` с нашего домена —
готовый носитель чужого скрипта, а `.exe` — способ раздать сотрудникам вредонос.

**Исправлено:** белый список из 27 расширений (документы, таблицы, изображения, архивы,
`.msg`/`.eml`). Проверка — в `WorkflowService.SaveAttachmentAsync` и `SaveBranchFileAsync`,
то есть на сервере, а не только в атрибуте `accept`. Файлы без расширения отвергаются.
Намеренно не разрешены: `.exe .dll .bat .cmd .com .scr .msi .ps1 .vbs .js .jar .hta .lnk .reg`,
веб-сценарии `.asp .aspx .php .jsp .cgi`, разметка `.html .htm .svg .xml`,
а также `.xlsm` (макросы Excel исполняются при открытии).

### 3.5 СРЕДНИЙ: инъекция формул в выгрузке CSV

`CsvExporter` экранировал кавычки и точку с запятой, но не знаки формул. Пользователь
с правом редактировать реестр мог вписать в наименование `=cmd|' /C calc'!A0` — и Excel
директора, открывшего выгрузку, выполнил бы команду (DDE).

**Исправлено:** значения, начинающиеся с `=`, `+`, `@`, табуляции или перевода строки,
а также с `-` (если это не число), получают ведущий апостроф и остаются текстом.
Отрицательные числа (`-1500`) не ломаются.

### 3.6 СРЕДНИЙ: не было заголовков безопасности и лимитов запросов

Ни одного защитного заголовка: страницу можно было встроить в iframe на чужом сайте
(clickjacking), браузер мог «угадать» тип скачанного файла, пароль подбирался без
ограничения числа попыток.

**Исправлено:** `SecurityHeadersMiddleware` и rate limiter — детали в таблице выше.

### 3.7 НИЗКИЙ: ключи Data Protection жили в профиле пула

Ключи, которыми шифруются cookie входа и antiforgery-токены, по умолчанию хранятся
в профиле пользователя пула приложений. Ресайкл пула = выход всех пользователей,
а в саду из нескольких процессов cookie одного процесса не читается другим.

**Исправлено:** ключи складываются в `C:\ProgramData\SnabDrive\keys` (настраивается
`Security:DataProtectionKeysPath`) и шифруются DPAPI на уровне машины. Если создать
папку не удалось, приложение продолжает работать со стандартным хранилищем и пишет
предупреждение в журнал при старте.

### 3.8 НИЗКИЙ: автомиграция схемы Identity в базовых настройках

`"AutoMigrateIdentitySchema": true` в `appsettings.json` означал, что боевой сайт
может сам пересоздавать схему. Перенесено в `appsettings.Development.json`;
в базовом файле и в шаблоне боевой конфигурации — `false`.

  ASP.NET Core Runtime приходят с Hosting Bundle, поэтому держите его свежим — уязвимости
  закрываются там, а не в ваших пакетах.

## 5. Как это настраивается

Все настройки — секция `Security` в `appsettings.json` / `appsettings.Production.json`:

```jsonc
"Security": {
  "EnableSecurityHeaders": true,       // false — снять все защитные заголовки (аварийный выключатель)
  "EnableHttpsRedirection": false,     // true — после настройки HTTPS (раздел 6)
  "HttpsPort": 443,
  "UpgradeInsecureRequests": false,    // true — браузер сам переводит http-запросы на https
  "CookieSecurePolicy": "SameAsRequest", // "Always" — cookie только по https (вместе с HTTPS)
  "DataProtectionKeysPath": "",        // пусто = C:\ProgramData\SnabDrive\keys
  "GlobalRequestsPerMinute": 1200,
  "ApiRequestsPerMinute": 600,
  "LoginAttemptsPerMinute": 10,
  "AllowedOrigins": []                 // пусто = кросс-доменные запросы запрещены
}
```

Три вещи, которые стоит знать:

1. **CSP** задан рекомендованным Microsoft набором для Blazor Server: свои скрипты и стили,
   ничего стороннего, `frame-ancestors 'none'`, `object-src 'none'`, `connect-src 'self' ws: wss:`
   (для циркула и SignalR). `'unsafe-inline'` оставлен только для стилей — разметка страниц
   использует атрибуты `style` (подсветка ячеек, рамки полей по ПКМ, «Звони»). Если какая-то
   страница вдруг поведёт себя странно, смотрите консоль браузера на сообщения
   «Refused to …» и правьте политику ключом `Security:ContentSecurityPolicy`.
2. **`AllowedHosts: "*"`** оставлен как есть, чтобы не сломать открытие сайта по IP.
   Как только известно боевое имя — впишите его в `appsettings.Production.json`
   (`"AllowedHosts": "snab.company.local;192.168.23.50"`): это закрывает подделку заголовка Host.
3. **Кто управляет пользователями.** Политика `ManageSystem` (Admin + Director) защищает
   «Пользователи», «Роли», «Обслуживание» и журнал. Если нужно, чтобы пользователей
   создавал только Admin, в `Program.cs` (строка с `AppPolicies.ManageSystem`) уберите
   `AppRoles.Director`. Не сделал это автоматически, чтобы не закрыть доступ человеку,
   который, возможно, им пользуется.

## 6. Включаем HTTPS (три настройки и сертификат)

> Полная пошаговая инструкция — как получить сертификат (Let's Encrypt, свой УЦ в AD,
> самоподписанный), привязать его в IIS и проверить результат — в **web/HTTPS.md**.

Сейчас перенаправление на https **выключено** — при отсутствии сертификата оно сделало бы
сайт недоступным. Порядок действий:

1. Получить сертификат (внутренний CA компании или Let's Encrypt, если сайт виден снаружи)
   и импортировать его в «Личное» хранилище компьютера на сервере.
2. В IIS: привязка сайта (Bindings) → добавить `https`, порт 443, выбрать сертификат.
3. В `appsettings.Production.json`:
   ```json
   "Security": {
     "EnableHttpsRedirection": true,
     "CookieSecurePolicy": "Always",
     "UpgradeInsecureRequests": true
   }
   ```
4. Перезапустить пул и проверить: `http://адрес` редиректит на `https://`, вход работает,
   в ответе есть заголовок `Strict-Transport-Security`.

Если IIS работает **out-of-process** (в `web.config` стоит `hostingModel="outofprocess"`),
приложение видит запрос как http и зацикливает редирект — в этом случае либо верните
`inprocess` (как в нашем `web.config`), либо настройте `ForwardedHeaders`.
